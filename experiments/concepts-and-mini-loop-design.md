# 개념 정리 + 개인 검증용 미니 루프 설계

> 2026-08-22, 준현. SPEC.md / PHILOSOPHY.md / interview_schema.md 스터디 + `experiments/one-shot-vs-loop-delta.md` 실측을 거치며 잡은 개념과, 다음 단계로 만들 개인 검증 스크립트의 설계.
> 목적 수정(2026-08-22): 팀 코드와 겹치는지는 더 이상 고려 대상이 아니다. 팀장이 AI 에이전트 로직 자체를 전문으로 하는 분이라 무엇을 해도 겹친다. 이 스크립트의 목적은 "안 겹치는 틈새 찾기"가 아니라, **이 프로젝트의 핵심 도메인(Generator/Judge 분리, 채점 신뢰성)을 직접 만들어보며 이해하고, 가능하면 실제로 쓸 만한 결과물이나 발견을 보태는 것.**

---

## 1. 원래 알고 있던 정의 (맞음, 확인됨)

> 사용자 도메인(목표)에 따라서 하네스를 만들어주고, 그 하네스를 목표를 달성할 때까지 계속 굴려서 점수로 하든 뭘로 하든 좋게 만든다. 결과적으로 사용자가 더 좋은 결과물을 얻을 수 있게 해줌.

점수는 그 자체가 목적이 아니라 **"목표값에 얼마나 가까워졌는지"를 시각적·데이터적으로 근거 있게 보여주는 증거**다. 그래서 그 점수가 거짓이거나 보여주기식이면 프로젝트 전체가 무너진다 — 이걸 막는 장치들이 원샷 대비 검증·동결·캘리브레이션·홀드아웃이다.

## 2. 용어 (경위는 `experiments/one-shot-vs-loop-delta.md` 실측 참고)

| 용어 | 쉬운 말 |
|---|---|
| 원샷 / 원샷 델타 | 한 번만 시킨 결과 / 반복 전후 점수 차이 — 반복이 실제로 의미 있는지 확인하는 관문 |
| 시험관 (judge) | 점수 매기는 쪽 |
| 동결 | 승인 후 채점 기준을 절대 못 바꾸게 잠금 |
| 캘리브레이션 | 사람이 먼저 채점해보고 AI 채점기랑 판단이 맞는지 확인 (승인의 전제조건) |
| 홀드아웃 | 반복시키는 쪽한테 절대 안 보여주는 평가 문제 |

## 3. 핵심 교정 — "정직한 에이전트"가 아니라 "에이전트를 정직하게 만드는 시스템"

이 프로젝트는 더 착한/정직한 AI 에이전트를 만드는 게 아니다. **Generator(고치는 쪽)는 자유롭게, 심지어 요령을 피워도 된다.** 대신 **Judge(채점하는 쪽)가 그 요령을 못 통과시키게 구조적으로 막는다.** 방지턱은 에이전트가 아니라 채점기 쪽에 있다.

- 실험(Generator)은 가변 — 얼마든지 멀티에이전트, 창의적으로.
- 판정(Judge)은 불변 — 승인 시점에 동결, 루프에 반응해 변하지 않음.

이 비대칭이 PHILOSOPHY.md가 말하는 정체성이다.

## 4. LLM 호출 vs 에이전트(제어) 로직 — 구분

- **LLM 호출** = API 한 번 부르는 것. 그 자체로는 "반복"이 안 된다.
- **에이전트 로직** = 그 호출을 언제·몇 번·어떤 입력으로 할지, 이전 결과를 보고 다음에 뭘 할지, 언제 멈출지를 코드로 결정하는 것. 이게 없으면 이 프로젝트는 성립하지 않는다 — "반복해서 고치기" 자체가 이 제어 로직이 하는 일이기 때문.

**단, 이 제어 로직 안에서 "채택할지 말지"는 LLM에게 맡기지 않는다.** 판정 재료(점수)만 LLM이 만들고, 판정 자체(채택/폐기, 종료 여부)는 코드가 결정한다. 여기를 LLM에게 맡기는 순간, 이 프로젝트가 막으려던 "자기가 만들고 자기가 검사하는" 문제가 되돌아온다.

## 5. 다음 단계 — 개인 검증용 미니 루프 설계

웹 화면·서버 없이, 로컬 스크립트로 Generator/Judge 분리가 실제로 작동하는지 검증한다.

```
experiments/
  one-shot-vs-loop-delta.md      # 원샷 델타 실측 파일럿 (기존)
  concepts-and-mini-loop-design.md  # 이 문서
  sandbox/                        # 개인 검증용 — 팀 제품 코드 아님
    config/
      task.example.json           # 목표 + 원본 자료 + 고정 루브릭 (사람이 직접 작성)
    generator.py                  # LLM 호출 1 — 개선안 생성 (Generator 역할)
    judge.py                      # LLM 호출 2, Generator와 별도 — 고정 루브릭 채점 (Judge 역할, 동결)
    loop.py                       # 오케스트레이터. LLM 호출 없음 — 순수 제어 로직
    report.py                     # 실행 기록을 마크다운 리포트로 출력
    run.py                        # 진입점 — config 읽고 loop 실행 후 report 생성
    runs/                         # 라운드별 산출물·점수·채택여부 기록 (json)
```

| 파일 | 역할 | LLM 호출 |
|---|---|---|
| `config/task.json` | 목표, 원본 자료, 고정 채점 기준 | 없음 |
| `generator.py` | 산출물 + 지난 피드백 → 개선안 | 1회 |
| `judge.py` | 고정 루브릭으로 채점, 홀드아웃 문제 관리 | 1회 (generator와 별도) |
| `loop.py` | Generator↔Judge 번갈아 호출, 라운드 카운트, 채택/폐기 판정, 정체 감지, 종료 조건 | **없음** — 신뢰성이 실제로 사는 곳 |
| `report.py` | 기록 → 마크다운 리포트 | 없음 |
| `runs/*.json` | 라운드별 기록 | — |

**진짜 제품(SPEC)과의 관계**: 팀장이 만드는 웹 화면(인터뷰 위저드·관제실)과 서버(생성 엔진), 그리고 실제 루프 엔진(Generator/Judge 오케스트레이션 자체)까지 — 이 전부가 팀장의 전문 영역(AI 에이전트)과 겹친다. 겹치는 걸 피하려고 만드는 게 아니라, **이 핵심 로직을 직접 짜봐야 "채점기가 실제로 안 흔들리는지"를 몸으로 검증할 수 있기 때문에 만든다.** 여기서 나온 코드나 발견이 실제로 팀 SPEC/구현에 반영될 수도 있고, 최소한 팀장과 같은 층위에서 기술 대화가 가능해지는 것 자체가 목표다.

## 6. 결정 (2026-08-22)

- **언어: Python** — LLM API 호출 + 단순 제어 로직에 빌드 과정 없이 바로 집중 가능. TS는 나중에 팀 루프 엔진(브라우저)에 옮길 때 재검토.
- **LLM: Claude 단일 모델로 시작, Generator·Judge 동일 모델** — provider를 처음부터 나누면 로직 검증 전에 복잡도만 늘어남. 단, 이 자체가 순환성 리스크를 살짝 남기므로 **2단계 실험으로 Judge만 다른 모델로 교체해 점수 흔들림을 비교** 예정.
- **1차 도메인: 운영체제(SYS-07) 재사용** — 이미 손으로 검증한 문제·정답 키가 있어서 "자동화해도 42→100 패턴이 재현되는가" 하나로 변수를 좁힘.

## 7. 미결
