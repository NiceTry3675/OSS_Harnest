# 체크리스트 — 내 트랙 (검증 엔진)

> 2026-08-22 기준. 제품 전체가 아니라 **내가 파는 축**(생성 엔진 + 검증 배터리 + 루프)의 진행 상황.
> 상태는 실제 코드 기준으로만 표시한다 — 주석에 언급만 있는 건 미구현으로 센다.

---

## 0. 큰 지도 — 제품 전체에서 내 위치

```
[인터뷰 위저드]  →  [생성 엔진]  →  [승인/캘리브레이션]  →  [루프 엔진]  →  [결과 화면]
     프론트          ★내 트랙★         ★내 트랙★           ★내 트랙★        프론트
```

내 트랙의 완성 기준: **자료 하나를 넣으면 → 채점표가 생성되고 → 그 채점표가 쓸만한지 검증되고 → 루프가 돌고 → 홀드아웃으로 재확인되는 것**이 코드로 끝까지 관통.

## 1. 이미 한 것

- [x] **루프 엔진 기본** — Generator ↔ Judge 왕복, 채택/폐기, 정체 감지, 조기 종료 (`loop.py`)
- [x] **동결** — 채점 프롬프트를 별도 파일로 분리 + SHA256 해시 잠금. 고치면 실행이 즉시 에러. 의도적 수정은 해시 재발급 = 재승인 (`judge.py`, `judge_prompt.frozen.*`)
- [x] **hard gate** — 결정적 검사, reject 시 LLM 채점 생략, 모르는 scorer는 실패 처리 (`judge.check_gates`)
- [x] **생성 엔진 (루브릭만)** — 자료+목표+분량제한 → 평가 문항·정답키 자동 생성 (`rubric_maker.py`, `make_task.py`)
- [x] **검증 배터리 4종 중 "안정성" 1종** — 산출물 고정 후 N회 재채점으로 채점 노이즈 분리 측정 (`measure_judge_noise.py`)
- [x] **원샷 베이스라인(라운드 0)** — 설정값이 아니라 모든 루프의 상수로 구현

## 2. 안 한 것 (미구현)

- [ ] **홀드아웃** — 전혀 없음. 방어 세트의 핵심인데 코드에 흔적조차 없음
- [ ] **검증 배터리 나머지 3종** — 순서 / 변별력 / 꼼수 내성
- [ ] **캘리브레이션** — 사용자 A/B 판정 vs 시험관 판정 대조. 승인의 전제조건인데 미구현
- [ ] **pairwise 채택** — 현재는 스칼라 엄격 개선(결정적 전용 특례). 문서의 기본 경로는 pairwise
- [ ] **Evaluation Pack** — 지금은 저지 프롬프트 해시만. 기준+게이트+판정절차+홀드아웃정책 전체를 묶는 팩과 definitionDigest 없음
- [ ] **생성 엔진의 나머지 산출물** — 게이트 생성, 홀드아웃 생성, 검증 리포트, 캘리브레이션 예시. 현재는 루브릭만 만듦
- [ ] **provenance 기록** — 쓰기 기록 없음

## 3. 다음에 할 것 (우선순위)

### 3-1. 지금 바로 — hard gate 켠 상태로 진짜 델타 실측

**왜 1순위**: SPEC §12 미결 6이 "1주차 원샷 델타 실측이 go/no-go"라고 못 박은 그 실측이다. 지금까지 실측이라고 한 것들은 전부 무효였다(과제에 압축 압력 없음 → 이후엔 게이트 미구현). 게이트가 켜진 지금이 처음으로 유효한 조건.

- [ ] `task.generated-os-chapter-900.json`으로 재실행
- [ ] Generator가 900자를 지키기 시작하는지 확인 (안 지키면 전 후보 실격 → 루프가 아무것도 못 배움)
- [ ] 지킨다면 그 상태에서 원샷 점수가 얼마인지 = **진짜 베이스라인**
- [ ] 최소 3회 반복 (노이즈 폭 안에 들어가는지 확인 — 이건 이제 습관으로)

**주의**: 전 후보 실격이면 루프가 방향을 못 잡는다. 그때는 3-2로.

### 3-2. reject vs cap 비교

**왜**: 실격(0점)은 피드백 신호가 없다. 모든 후보가 0점이면 "뭐가 나은지"를 루프가 알 수 없다. 스키마 v0.3이 `onFail: "cap"`(점수 상한)을 따로 둔 이유가 이것일 가능성.

- [ ] `cap` 모드 구현 (코드는 이미 있음, config만 바꾸면 됨)
- [ ] 같은 과제를 reject / cap 두 모드로 돌려 루프 거동 비교
- [ ] **문서에 없는 것**: 어느 쪽이 학습 신호로 나은지 — 스키마는 둘 다 제공만 하고 언제 뭘 쓸지는 안 정함

### 3-3. 홀드아웃 구현

**왜**: 방어 세트에서 유일하게 손도 안 댄 항목이고, "본 적 없는 문제에서도 +N점"이라는 제품의 최종 증거가 여기서 나온다.

- [ ] 생성 엔진이 문항을 만들 때 가시/홀드아웃 분할
- [ ] 불변식 구현: 홀드아웃 문항이 Generator 프롬프트에 **절대** 안 들어가게
- [ ] 홀드아웃 채점은 라운드 0과 종료 시에만 (파생 신호 유입 금지)
- [ ] **검증**: Generator에게 나간 프롬프트를 전부 로그로 남기고, 홀드아웃 문항 문자열이 등장하는지 grep으로 확인 = 문서가 말하는 "코드로 감사 가능"의 실체

### 3-4. 검증 배터리 "순서" 검사

**왜**: 생성 엔진이 만든 루브릭이 **좋은 루브릭인지 아무도 검증 안 하고 있다.** 순서 검사(좋은 답이 실제로 높은 점수를 받는가)가 제일 기본이고, 만들기도 쉽다.

- [ ] 품질 등급이 다른 산출물 3개 준비(좋음/보통/나쁨)
- [ ] 채점 순서가 품질 순서와 일치하는지 확인
- [ ] 안 맞으면 그 루브릭은 못 쓴다 = 생성 엔진 개선 신호

### 3-5. 다른 도메인 재현

**왜**: "템플릿은 예시일 뿐, 엔진은 도메인 무관"이라는 문서 주장을 실증한다. 코드 수정 없이 자료 파일만 바꿔서 되면 증명 끝.

- [ ] 정처기(DB 정규화) 또는 다른 과목 자료로 `make_task.py` 실행
- [ ] 코드 한 줄도 안 고치고 되는지 확인
- [ ] 문항 유형별 노이즈가 재현되는지 (현재 n=1 관찰)

## 4. 의문 목록 — 관심 갖고 볼 것

실험하면서 답이 나올 수도 있고, 문서에 없어서 팀에 물어볼 수도 있는 것들.

### 이미 반쯤 관측된 것

- [ ] **loser's curse** — 베이스라인은 딱 한 번 채점되는데, 그 한 번이 짜게 나오면 델타가 부풀려진다. 문서는 winner's curse만 막음. → 베이스라인 다회 채점(중앙값)의 효과를 재보면 근거가 생김
- [ ] **비교·판단형 문항이 노이즈원인가** — 현재 n=1. 8문항짜리 새 루브릭에는 비교판단이 5개 있으니 재현 확인 가능
- [ ] **티어 양방향 리스크** — 무료(약한 모델)는 노이즈 오염, BYO(강한 모델)는 델타 소멸. 문서는 한 방향만 경고

### 아직 안 건드린 것

- [ ] **문항 수가 점수 해상도를 결정한다** — 8문항 × (0/0.5/1)이면 최소 단위가 6.25점. 노이즈가 4.4점이면 **"1단계 개선"과 "노이즈"가 거의 같은 크기다.** 문항 수를 늘리면 해상도가 올라가는데 비용도 올라감. 문서에 문항 수 가이드가 없음
- [ ] **생성 엔진과 Generator가 같은 모델일 때 순환성** — 문서 §8은 캘리브레이션으로 끊는다고 했는데, 내 sandbox엔 캘리브레이션이 없다. 그럼 지금 내 결과는 순환성에 노출된 상태
- [ ] **홀드아웃 문항이 가시 문항과 너무 비슷하면?** — 생성 엔진이 8문항을 한 번에 만들고 그중 2개를 홀드아웃으로 빼면, 내용이 겹쳐서 "본 적 없는 문제"가 아닐 수 있다. 문서는 홀드아웃 분할 정책만 있고 **다양성 보장은 없음**
- [ ] **정답 키를 agent가 만들면, 그 정답 키가 틀렸을 때 누가 잡나** — 사용자가 기출 정답을 안 가진 경우(대부분) 생성 엔진이 정답 키까지 만든다. 그게 틀리면 채점 전체가 틀린다. 스키마는 `expectedAnswer` 없으면 "주의" 표시만 함
- [ ] **압축률이 얼마여야 트레이드오프가 생기나** — 2.4배 팽창(=압축 아님)에선 원샷 만점, 3.4배 압축에선 62점. **그 사이 어디에 경계가 있는지** 모름. 템플릿 설계 파라미터가 됨

## 5. 완성 기준 (내 트랙)

- [ ] 자료 파일 하나 → 채점표 생성 → 검증 배터리 통과 → 루프 실행 → 홀드아웃 재확인까지 **코드 한 줄 안 고치고** 관통
- [ ] 도메인 2개 이상에서 위가 재현
- [ ] 각 실행이 최소 3회 반복돼 노이즈 폭과 함께 보고됨
- [ ] 홀드아웃 불변식이 로그 검사로 증명됨
