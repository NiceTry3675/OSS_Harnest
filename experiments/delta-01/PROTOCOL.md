> SPEC §12 미결 6의 실행 문서. 인수인계·온보딩 문서 템플릿의 **원샷 델타 go/no-go**를 판정한다.

> 2026-08-22 작성.

## 1. 대상 저장소 — NousResearch/hermes-agent (폴백 없음)

선정 사유 (2026-08-22, 채점 전 기록):
- **오염 최소 기대**: 2026-02 출시로 대부분 모델의 학습 컷오프 이후. 단, 이 기대는 추정이므로 §5의 무문서 프로브로 **실측 검증**한다.
- **케이스 볼륨**: `label:question` 닫힌 이슈 81건 (2026-08-22 확인) — 큐레이션 여유.
- **온보딩 갭의 실증**: 서드파티 문서 저장소(hermes-agent-docs, awesome-hermes-agent)가 존재한다는 것 자체가 공식 온보딩 문서의 공백을 증명 — 템플릿 서사와 정합.
- **폴백 없음 (2026-08-22 결정)**: 무문서 프로브 실패 시 다른 저장소로 갈아타지 않고 **중단 후 재논의**한다. 결과가 나쁠 때 조건을 갈아끼우는 체리피킹 경로를 두지 않는다.

## 2. 케이스 추출 규칙

**전제 주의(2026-08-22): 닫힌 이슈 ≠ 정답 있는 Q&A.** 닫힘은 스테일 봇, 중복, 무응답 포기, "PR로 수정됨" 링크만 남은 경우를 포함한다. 아래 2단 필터가 이 간극을 걸러낸다.

### 2.1 모집단
`repo:NousResearch/hermes-agent is:issue is:closed label:question` — 수집 시점 스냅숏을 `raw/`에 캐시하고 수집 일시를 기록한다.

### 2.2 기계 필터 (collect.py)
1. 작성자 본인·봇(`[bot]` 로그인) 제외 코멘트 ≥ 1
2. 질문 본문 ≥ 100자
3. 답변 후보 코멘트: 작성자 외·봇 외, ≥ 200자, 링크 밀도 < 50%(링크만 던진 답변 제외)
4. 답변 후보가 0개면 탈락

`state_reason`은 게이트가 아니라 기록 메타데이터다 (2026-08-22 개정, 동결 전): 초안은 `completed`만 통과시켰으나, 첫 수집에서 이 저장소가 답변된 질문도 not_planned로 닫는 관행이 확인됨(58건 중 46건이 not_planned). 답변 존재는 닫힘 사유가 아니라 스레드 내용(§2.3)으로 판정한다 — "닫힌 이슈 ≠ Q&A" 주의의 올바른 적용은 메타데이터 신뢰가 아니라 내용 판독이다.

### 2.3 의미 큐레이션 (사람/Claude 판독 — CURATION.md에 전건 기록)
각 후보에 keep/drop + 사유 한 줄. **drop 사유도 남긴다** — 큐레이션 자체가 provenance다.
- (a) 실질 질문인가 — 버그 리포트·기능 요청으로 흐른 것 제외
- (b) 스레드 안에 **실제로 답이 존재**하는가 — 닫혔지만 답이 없는 것 제외
- (c) 답이 **자기완결적**인가 — 외부 링크·코드 diff를 따라가야만 이해되는 답 제외
- (d) **문서로 답할 수 있는 종류**인가 — 특정 환경 디버깅·일회성 사고 조사 제외
- (e) **클러스터 중복 제거** (2026-08-22 추가, 동결 전) — 같은 근본 질문의 중복 이슈는 최선 답변 1건만 keep. 중복을 다 실으면 가시/홀드아웃에 같은 답이 걸쳐 앉아 "커버리지"가 부풀려진다

큐레이션 중 확인된 도메인 특성 (기록): 이 저장소의 답변 다수는 `hermes-sweeper`(기여자 계정으로 게시되는 자동화 리뷰)가 작성한다 — 문서·파일 경로를 인용하는 실질 답변이라 정답으로 인정하되, 케이스별로 출처(사람/스위퍼)를 기록한다. 프로젝트가 질문 응대 봇을 자체 제작했다는 사실 자체가 온보딩 갭(§1)의 추가 증거다.

### 2.4 정답 선택 규칙 (우선순위)
1. 질문자가 확인한 답변(후속 코멘트에 감사·해결 표시)
2. 닫힘 직전의 실질 답변 코멘트
3. 둘 다 없으면 drop

### 2.5 시간 분할
큐레이션 통과 케이스를 `created_at` 오름차순 정렬 → 앞 2/3 가시(상한 25), 뒤 1/3 홀드아웃(10~15 목표). **케이스 확정 후 변경 금지.** 최근 이슈가 홀드아웃이 되므로 분포 이동이 실전(미래 질문)과 같은 방향이다.

## 3. 산출물과 생성 원료

- **산출물**: "Hermes Agent 신규 사용자 온보딩 FAQ 문서" (영문 — 케이스 언어와 일치).
- **분량 hard gate**: 문서 토큰 ≤ 가시 케이스 원료 총 토큰의 15% (원료 확정 후 절대값으로 1회 환산해 동결. 위반 = 실격). 압축을 강제해 "가시 답변 통째 삽입" 꼼수를 구조로 막는다.
- **생성 원료** (모든 조건 동일): 가시 케이스의 Q&A 쌍 전체 + 저장소 README 발췌(고정 스냅숏). **홀드아웃 케이스는 어떤 조건의 어떤 단계에도 노출 금지.**

## 4. 동결 평가자

- **case_answering**: responder는 [문서 + 케이스 질문]만 본다(원료·정답·타 케이스 비노출) → grader가 정답 대조 — "정답의 핵심을 담는가" 단일 check, 0 / 0.5 / 1 → 케이스 평균 × 100.
- **hard gate**: 분량 초과 = 실격.
- **암기 검사(결정적, 보고용)**: 문서와 가시 정답 간 13-gram 중복률.
- **평가자 구성 동결 (v1, 2026-08-22)**: 프롬프트 = harness.py의 `P_RESPONDER`·`P_GRADER`·`P_DOC_BLOCK`, 디코딩 = responder·grader temp 0.0 / 생성 temp 0.7, 척도 = 0/0.5/1 단일 check. 실행 제공자 = Vertex AI(서비스 계정), 모델 = `gemini-3.7-flash`(체험 티어 구성과 동일). 이후 변경 금지.

## 5. 비교 조건 (생성 예산 동일화: 생성 콜 10회)

| # | 조건 | 정의 |
|---|---|---|
| ⓪ | 무문서 프로브 | responder에 질문만. **저장소 적합성 게이트 겸 오염 측정** |
| ① | 원샷 | 원료 → 1콜 생성 (라운드 0 기준선) |
| ② | 반복 첨삭 | "더 개선해줘" 10회 직렬. 점수·트레이스 피드백 없음 |
| ③ | Harnest 루프 | 10라운드. 가시 채점 + **케이스 트레이스** 피드백 → 변이 → 제3 채택 모드(가시 스칼라 엄격 개선 시 채택, 동점은 챔피언 유지) |
| ④ | best-of-10 | 독립 10콜 생성 → 가시 점수 최고 선택 |

- 채점 콜 수는 조건마다 다르다(③·④만 루프 중 채점) — 은폐하지 않고 조건별로 분리 보고한다. 예산 동일화의 단위는 **생성 콜**이다.
- **무문서 프로브 게이트**: 전체 케이스 무문서 정답률 < 30% → 통과 / 30~50% → 주의(오염 의심 케이스 개별 drop 후 재산정 1회 허용, 사유 기록) / > 50% → 저장소 부적합, **중단**(§1 폴백 없음).

## 6. 홀드아웃 불변식

- 홀드아웃 채점은 **라운드 0과 종료 시에만** 수행한다.
- 홀드아웃 점수·트레이스에서 파생된 어떤 신호도 생성·채택·중단 판단에 유입되지 않는다.

## 7. 실행 구성

- **본 실행 (go/no-go 판정 기준)**: 체험 티어 구성 — generator·responder·grader 전부 `gemini-3.7-flash`, 10라운드, 빔 1.
- 보조 실행(옵션, 서사용): 강한 모델 1회 — 판정에는 불사용.

## 8. 성공 조건 (SPEC §12 미결 6)

go = 아래 전부 충족:
1. ③의 **홀드아웃** 점수 > ①, 그리고 > ②
2. ③의 gate 위반이 ① 대비 비증가
3. 암기 검사에서 통째 삽입 없음(분량 게이트 통과 + 13-gram 중복률 이상 없음)
4. (보고 항목) ③ vs ④ — 우위 또는 동등이면 방어 카드 강화, 열세면 그대로 보고

no-go 시: 도메인 전체를 버리기 전에 케이스 유형별(태그별) 분해로 델타가 사라지는 지점을 좁힌다.

## 9. 델타 02 개정 (2026-08-22 — 채점 전 동결)

델타 01의 no-go 원인 분해(report.md)에 따른 개정. 변경은 원인에 대응하는 항목으로 한정하며, 평가자(§4)·비교 조건(§5)·예산·홀드아웃 불변식(§6)·실행 구성(§7)·성공 조건(§8)은 **변경하지 않는다**.

1. **모집단 확대** (원인: 케이스 26건 → 압축 압력 부재). `label:question`(81) → 닫힌 이슈 전체(11,463)에서 질문형을 로컬 판별: 제목에 `?`·`？`, 질문사 시작(how/what/why/can/does/where/when/should/is it/help/question), `[Setup]`·`[Question]`·`[Inquiry]` 태그, `question`·`support`·`docs` 라벨. 판별 규칙은 collect_v2.py에 코드로 고정.
2. **답변 후보 강화 필터** (규모 대응): 답변 코멘트는 COLLABORATOR/CONTRIBUTOR/MEMBER/OWNER 작성 **또는** 질문자 확인(ack) — v1 keep 전건이 이 조건을 만족했음을 근거로 승격.
3. **반복성 보존 분할** (원인: 클러스터 dedup이 질문 반복성 — 이 템플릿의 가치 원천 — 을 삭제). **시간 분할을 먼저** 수행하고, 동근원 중복 병합은 **가시 세트 내부에만** 적용한다(원료 이중 계상 방지). 홀드아웃 시대의 반복 질문은 **보존한다** — "가시 시대의 질문이 미래에 반복된다"가 측정 대상 그 자체다. 델타 01의 §2.3-(e) 전면 dedup 규칙은 이 설계 오류로 판정, 폐기.
4. **분량 게이트: 절대값 5,000자** (원인: 상대 15% 게이트가 원샷 자연 길이보다 커서 미작동). "읽을 만한 온보딩 문서"의 자연 제약으로 설정. 단서: 원샷 자연 길이가 5,000자를 하회하면 게이트 미작동이 재발한 것이므로 결과 보고에 명시하고 중단·재설계한다(조용한 재조정 금지).
5. **세트 목표**: 가시 상한 45, 홀드아웃 20~30. 무문서 프로브 게이트(§5)와 만점 케이스 drop 절차는 동일 적용. (실집계 기록, 2026-08-22: keep 84 → 가시 45→병합 후 39, 홀드아웃 39 — 상한 30 초과분을 자르지 않고 유지한다. 반복 케이스 보존과 통계 안정성이 우선이고, 홀드아웃 채점은 라운드 0·종료 시에만이라 비용 영향이 미미하다. 케이스를 골라 빼는 개입이 더 나쁘다.)

### 9.1 델타 02b — 생성 프롬프트 개정 (2026-08-22, 실행 중 기록)

02a 실행 결과 **전 조건이 분량 게이트 초과로 실격 출발**했다: 원샷 6,085자, 전 후보 5,118~6,690자(runs2a/ 보존). 문자 수 상한은 지시만으로 준수 불가한 모델 한계로 확인 — 루프는 실격 트레이스를 받았으나 10라운드 내 5,000자 이하 후보를 한 번도 생성하지 못했다(곡선 0 평평).

개정: **생성 프롬프트(P_ONESHOT·P_ITERATE·P_MUTATE)에 여유 목표를 명시** — "hard limit {cap}자(초과=실격 0점), 목표 {cap×0.8}자(≈단어 수 앵커)". 단어 수 앵커는 LLM이 문자보다 단어를 더 잘 세는 특성 반영.

**불변 확인**: 평가자(§4)·게이트 값(5,000자)·케이스 세트·채택 규칙·예산은 변경 없음. 생성 프롬프트는 실험하는 쪽(Generator)의 공학이며 판정 절차가 아니다 — "실험은 가변, 판정은 불변". 02a 결과는 runs2a/에 보존하고 리포트에 병기한다(실격 출발의 서사 가치: 원샷은 제약을 어기고, 그 사실 자체가 트레이스로 보인다).

### 9.2 델타 03 — 기여 분리 측정 (2026-08-22, 채점 전 동결)

02b의 go 판정은 유지된다 — 03은 판정이 아니라 **해석의 분해**다: 루프 승리의 원천이 (a) 실격 신호를 받는 재시도 기회인지, (b) 스칼라 점수 피드백인지, (c) 케이스 트레이스의 내용인지를 사다리식 비교로 분리한다. 평가자·게이트·케이스·예산(생성 콜 10) 불변.

| # | 조건 | 피드백 | 분리하는 기여 |
|---|---|---|---|
| ⑤ 실격 재시도 | 실격 사실 + 길이 수치만(트레이스·점수 없음). 준수 문서가 나오면 정지 | ⑤−① = 실격 신호·재시도 |
| ⑥ 점수-온리 루프 | 가시 스칼라 점수만(트레이스 없음). 제3 채택 모드 동일 | ⑥−⑤ = 점수 피드백 |
| ③ (02b 기존) | 점수 + 케이스 트레이스 | ③−⑥ = 트레이스 내용 |

주의 기록: 02b의 ③에서 채택된 유일한 라운드(1)의 트레이스는 게이트 실격 한 줄뿐이었다(실격 시 evaluate가 케이스 채점을 생략하므로). 즉 02b 데이터만으로는 ③−⑥≈0이 이미 시사되며, 03은 이를 명시 측정으로 확정하고 ⑥이 준수 이후 구간에서 점수만으로 개선을 만드는지("점수만 피드백하면 개선 없음" 가설)를 검증한다.
