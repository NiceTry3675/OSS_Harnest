## 1. 왜 지금 이것인가

`b3a1751`로 인수인계 템플릿과 BYO Gemini 클라이언트가 탑재됐다. 그런데 SPEC이 스스로 이렇게 적어뒀다:

> 모의 모델 E2E 관통(원샷 50→루프 100, 홀드아웃 불노출 검증). **잔여: 실키 BYO 실검증(CORS 실측 겸용 — 미결 3)**

즉 **코드는 있으나 진짜 키로 돌아간 적이 없다.** 통과한 E2E는 전부 결정적 모의 모델(`createMockClient`)로 한 것이고, 실제 네트워크는 한 번도 타지 않았다.

그리고 §10이 CORS를 "프론트 투자보다 선행하는 실측 2건" 중 하나로 규정했는데, 순서가 뒤집혀 있다 — 프론트와 LLM 클라이언트가 먼저 올라왔고 이 검증이 남았다. **지금 스켈레톤은 미검증 전제 위에 서 있다.**

### 무엇이 걸려 있는가

SPEC §4.2의 약속: *"BYO 경로는 키·민감 텍스트가 서버를 거치지 않음"*. 브라우저에서 벤더 API로 직행이 안 되면 서버를 경유해야 하고, 그러면 이 약속이 깨진다. 플래그십이 인수인계 문서(= 사내 질문·답변 로그)라 민감도가 높아 **프라이버시가 마케팅이 아니라 요건**이다.

## 2. 검증 대상 (미결 3의 확장된 범위)

> 실측 대상은 BYO 직행 3사 + 커스텀 프로바이더 대표 2종(OpenRouter, 로컬 Ollama — 2026-08-22 확장)

| # | 벤더 | 현재 구현 | 검증 방식 |
|---|---|---|---|
| 1 | **Gemini** | `createGeminiClient` 있음 | **실제 앱 코드 경로로** 검증 |
| 2 | Anthropic | 없음 | 프로브로 검증 |
| 3 | OpenAI | 없음 | 프로브로 검증 |
| 4 | OpenRouter | 없음 | 프로브로 검증 |
| 5 | 로컬 Ollama | 없음 | 프로브로 검증 |

**1번은 프로브를 새로 만들지 않고 앱을 그대로 쓴다.** 별도 프로브로 확인하면 "프로브는 되는데 앱은 안 되는" 간극이 남는다. 실제 출시되는 코드(`apps/web`)로 검증해야 검증이 의미를 갖는다.

## 3. 검증 질문

1. **호출 성공 여부** — 응답이 오는가 / CORS로 차단되는가
2. **프리플라이트** — 커스텀 헤더로 인해 브라우저가 보내는 사전 확인(OPTIONS)이 통과하는가
3. **에러 판독** — 401/400 응답의 **본문을 읽을 수 있는가**. 못 읽으면 "키가 틀렸습니다" 같은 안내가 불가능하다
4. **재시도 로직과의 상호작용** (Gemini 한정) — `createGeminiClient`는 실패를 3회 재시도한다. **CORS 차단은 재시도해도 절대 안 풀리는 종류의 실패**인데, 현재 코드는 이를 구분하지 않아 1.5s+3s+4.5s를 낭비하고 원인 불명 에러를 던진다. 실측으로 확인하고 개선 제안 여부를 판단한다.

1·2가 판정 대상, 3·4는 기록·개선 제안 항목이다.

## 4. 사전 등록 — 예상과 판정 규칙 (실행 전 작성)

### 4.1 SPEC의 사전 조사 (검증 대상 명제)

> Anthropic 공식 지원(전용 헤더), Gemini 지원, OpenAI 동작하나 비공식

**이 문장이 맞는지가 검증 대상이다.** 문서에 그렇게 써 있다는 것은 근거가 아니다.

### 4.2 벤더별 예상

| 벤더 | 예상 | 확인할 것 |
|---|---|---|
| Gemini | 통과 | 앱 코드 경로 그대로 도는가 |
| Anthropic | 전용 헤더 필요 | 헤더 없이는 실패하는가 (있어야만 되는지 확인) |
| OpenAI | 통과하나 비공식 | 실제 동작 여부. 문서화 안 됨 = 예고 없이 바뀔 위험 기록 |
| OpenRouter | 미상 | — |
| Ollama | 기본 차단 예상 | 로컬 서버라 사용자가 CORS 설정을 켜야 할 가능성 |

**예상이 빗나가면 그대로 기록한다.** 예상에 맞추려 요청을 바꿔가며 시도하지 않으며, 시도한 변형은 성공·실패 관계없이 전부 남긴다.

### 4.3 판정 규칙 (결과를 보기 전에 확정)

| 결과 | 판정 | 후속 |
|---|---|---|
| Gemini 통과 | **현 구현 유효** | 나머지 벤더는 어댑터 추가 대상으로 정리 |
| Gemini 차단 | **심각** — 현재 main의 BYO 경로가 동작하지 않음 | 즉시 보고. 설계 변경은 팀 결정 |
| 일부 벤더만 통과 | **부분** | 통과 벤더만 BYO 지원, 나머지는 화면에 "미지원" 명시 |
| Ollama 차단 | 예상 범위 | 사용자 측 설정 안내 문서화로 처리 가능한지 검토 |

**전부 차단이어도 "그럼 프록시 쓰면 되지"로 넘어가지 않는다.** 그것은 SPEC §4.2의 프라이버시 약속을 바꾸는 설계 변경이며 실무자가 단독 결정할 사안이 아니다 — 중단하고 보고한다.

## 5. 방법

### 5.1 원칙 — 문서를 읽지 않고 실제로 호출한다

벤더 문서에 "CORS 지원"이라 써 있어도 근거로 삼지 않는다. **실제 브라우저에서 실제 API를 호출해 실제 응답을 받는다.** 이 항목에서 위험한 지점이 정확히 "문서와 실제의 불일치"다.

### 5.2 Gemini — 앱 경로

`npm run dev`로 개발 서버를 띄우고, 인수인계 템플릿에 BYO 키를 입력해 실제 루프를 1회 돌린다. 관제실 화면에 실제 점수가 찍히면 통과.

- 실행 위치는 `http://localhost:5173` — `file://`은 출처가 `null`이라 실제 환경과 다르므로 쓰지 않는다.
- 모의 모델이 아니라 실제 Gemini가 호출됐음을 네트워크 탭으로 확인한다.

### 5.3 나머지 4종 — 프로브

`experiments/byok-cors/probe.html`. 개발 서버에서 서빙해 같은 출처 조건으로 실행한다.

- 키 입력값은 **어디에도 저장하지 않는다** (메모리만, 새로고침 시 소멸)
- 벤더별 최소 비용 요청 1회 — 짧은 프롬프트, 출력 토큰 상한 최소
- 결과 표시: 성공 / CORS 차단 / HTTP 에러(코드·본문 판독 가능 여부) / 네트워크 에러

### 5.4 기록

`experiments/byok-cors/report.md`에 벤더별로:

- 요청 방식(엔드포인트·헤더)
- 결과
- 실패 시 브라우저 콘솔 원문 그대로
- 시도한 변형 전부
- **검증 일시** — CORS 정책은 벤더가 예고 없이 바꾼다. 이 결과에는 유효기간이 있으며 출시 전 재확인이 필요하다.

## 7. 부수 산출물 (검증 중 확인되면 별도 제안)

구현 제안은 이 문서의 판정 대상이 아니며, 실측 결과에 근거가 생겼을 때만 낸다.

- **CORS 실패의 조기 판별** (§3-4) — 재시도로 안 풀리는 실패를 구분해 fail-fast
- **연결 테스트(ping)** — SPEC 미결 7이 요건으로 명시: *"커스텀 endpoint는 실행 전 연결 테스트(1콜 ping)로 CORS·인증을 fail-fast — 루프 중간이 아니라 시작 전에 막히게"*. 현재 미구현.
