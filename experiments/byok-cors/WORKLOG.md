## 1. 범위

```
잔여: 실키 BYO 실검증(CORS 실측 겸용 — 미결 3), 캘리브레이션·검증 리포트, 프록시 경로
```

`b3a1751` 시점의 BYO 경로(`apps/web/src/lib/llm.ts`)는 테스트 38개가 전부 결정적 모의 모델(`createMockClient`) 기준이며, 실제 네트워크 호출은 검증되지 않았다.

**범위 밖**: 벤더 어댑터 추가, 키 보관 정책 변경, 프록시 경로. 검증 결과가 이들 설계의 전제이므로 검증을 선행한다.

## 2. 검증 필요성

SPEC §10은 CORS 검증을 *"프론트 투자보다 선행하는 실측 2건"* 중 하나로 규정한다. 현재 델타 실측은 완료(go)이나, CORS 미검증 상태에서 프론트·LLM 클라이언트가 구현됐다.

브라우저 직행이 불가능할 경우 서버 경유가 강제되며, 이는 SPEC §4.2의 *"BYO 경로는 키·민감 텍스트가 서버를 거치지 않음"* 을 무효화한다. 플래그십(인수인계·온보딩)의 입력이 사내 질문·답변 로그이므로 이 조건은 기능 요건에 해당한다.

## 5. 입력 데이터의 설계 결함 — 후속 작업 시 필독

본 검증의 인터뷰 입력(배포 파이프라인 업무 자료 + 질문·답 4쌍)은 검증 진행을 위해 작성한 것으로, 실제 업무 로그가 아니다. 여기서 나오는 **점수 자체는 실제 LLM이 산출한 실측값이며 조작되거나 모의된 값이 아니다.** 문제는 값의 진위가 아니라 **과제 설계**에 있다.

**결함 1 — 홀드아웃이 재료에 포함돼 있다.** 작성한 자료가 4개 주제(배포 절차·DB 접속·배포 실패·알림)를 모두 담고 있고, 질문 4개가 정확히 그 4개 주제다. 따라서 홀드아웃으로 분리된 1건의 답도 이미 재료 안에 있다. 문서가 재료를 고르게 압축하기만 하면 자동으로 커버되므로 **"본 적 없는 질문에 통하는가"를 측정하지 못한다.**

대비: `delta-01`의 설계는 *"홀드아웃 케이스는 어떤 조건의 어떤 단계에도 노출 금지"* 이며, 홀드아웃이 시간상 나중의 실제 이슈라 그 답이 재료에 없을 수 있다. 분포 이동이 실전과 같은 방향이다.

**결함 2 — 출제자와 자료 작성자가 동일하다.** 질문이 자료로부터 답할 수 있게 작성됐으므로 난이도가 통제되지 않았다.

**결함 3 — n=4.** 가시 3 / 홀드아웃 1. 1건이 점수의 100%를 좌우한다.

### 측정 대상별 유효성

| 측정 대상 | 유효 여부 | 근거 |
|---|---|---|
| CORS 통과 여부 | **유효** | 벤더 서버의 HTTP 응답 코드로 판정된다. 입력 내용과 무관하며 자료에 임의 문자열을 넣어도 결과가 같다 |
| 루프 완주·체크포인트·재개 등 **동작** | **유효** | 기능 작동 여부이며 내용에 의존하지 않는다 |
| 산출된 점수 | **실측값이나 해석 불가** | 값 자체는 진짜다. 다만 위 결함 1~3으로 인해 개선 폭·홀드아웃 전이 등 **어떤 일반화도 지지하지 않는다** |

**후속 작업 규칙**: 이 실행의 점수를 델타·성능 주장에 인용하지 않는다. 개선 폭 측정이 목적이라면 `experiments/delta-01`의 설계 요건 — 제3자가 만든 실제 데이터, 홀드아웃 비노출, 시간 분할, 오염 프로브 — 을 갖춘 별도 실측이 필요하다.

## 6. 미해결

1. **실키 루프 완주 미관측** — 연속 503으로 라운드 0을 통과하지 못했다(0/8, 상태 대기). 검증된 것은 벤더 도달 가능성이며, 실키 조건에서의 루프 완주는 미확인. **재개 시 목표는 §5 기준의 "동작 확인"에 한정하며, 점수는 기록하되 해석하지 않는다**
2. Anthropic — 키 확보 시 검증. 전용 헤더(`anthropic-dangerous-direct-browser-access`) 필요 여부 포함
3. OpenRouter / Ollama — 미결 3의 커스텀 프로바이더 대표 2종
4. 브라우저 1종(Chrome)만 확인

## 7. 프로토콜 정정

초안 §3.3·§5.3의 *"응답 헤더 중 CORS 관련 항목 표시"* 는 실행 불가하다. 브라우저 명세상 JS는 `Access-Control-*` 응답 헤더에 접근할 수 없다. 성공/실패 역산으로 대체했으며, 이는 판정 근거를 좁히는 방향이므로 기준 완화에 해당하지 않는다.

## 8. 관찰 사항 (제안 보류)

실측 표본이 1일차에 한정되므로 기록만 남긴다.

1. **재시도가 실패 유형을 구분하지 않는다.** `createGeminiClient`는 모든 실패를 3회 재시도(총 9초)한다. 503은 재시도가 유효하나 CORS 차단은 재시도로 해소되지 않는다. 현행 대상 벤더에서는 발동하지 않으며, 미결 7의 커스텀 endpoint 도입 시 발생한다. 미결 7이 요건으로 명시한 *"실행 전 연결 테스트(1콜 ping)로 fail-fast"* 와 동일 사안이다.

2. **429와 503이 동일하게 표시된다.** 체험 티어는 일일 한도 소진(429)과 서버 과부하(503) 양쪽에 노출되며 대처가 다르다. 현재 표시는 `Gemini HTTP 5xx` 단일 형태다.

3. **체크포인트·재개 정상 동작.** 오류 시 체크포인트 보존 안내와 재시도 경로가 제공된다.
