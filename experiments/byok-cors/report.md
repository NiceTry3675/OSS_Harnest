## 앱 코드 경로 실검증 (PROTOCOL §5.2)

프로브는 벤더 API 도달 가능성만 확인한다. 실제 출시되는 코드(`apps/web`)로도 확인해야 "프로브는 되는데 앱은 안 되는" 간극이 없다.

> **입력 데이터 주의**: 아래 실행의 인터뷰 입력(업무 자료 + 질문·답 4쌍)은 검증 진행을 위해 작성한 것이다. 산출되는 점수는 실제 LLM의 실측값이나, **홀드아웃의 답이 재료에 포함돼 있어 "본 적 없는 질문" 측정이 성립하지 않으며**(그 외 결함 2건), 개선 폭·홀드아웃 전이 등 어떤 일반화도 지지하지 않는다. CORS 판정은 벤더 서버의 HTTP 응답 코드로 결정되므로 이 결함의 영향을 받지 않는다. 상세: [WORKLOG.md §5](WORKLOG.md).

**실행**: `npm run dev` → 인수인계·온보딩 템플릿 → 케이스 4건(가시 3 / 자동 홀드아웃 1) → 분량 2,000자 → **채점 모델 Gemini(BYO)** 로 승인 → 관제실에서 실행.

**결과** — 브라우저 콘솔:

```
POST https://generativelanguage.googleapis.com/v1beta/models/gemini-3.7-flash:generateContent
503 (Service Unavailable)                                              llm.ts:33
```

**CORS 통과 확인.** 근거:

- 요청 출처가 `llm.ts:33` — 프로브가 아니라 **`createGeminiClient`의 실제 fetch 호출**이다.
- 브라우저가 **HTTP 상태 코드(503)를 읽었다**. CORS로 차단되면 상태 코드에 접근할 수 없고 `TypeError: Failed to fetch`만 남는다.
- 즉 실패 원인은 CORS가 아니라 **벤더 서버의 일시적 과부하**다.

앱 화면에도 `모델 호출 중 오류가 발생했습니다: Gemini HTTP 503`이 표시됐다 — 에러 본문 판독이 가능하다는 뜻이며, 이는 §3-3(에러 판독) 항목의 확인이기도 하다.

## 판정 (PROTOCOL §4.3 규칙 적용)

> Gemini 통과 → **현 구현 유효**. 나머지 벤더는 어댑터 추가 대상으로 정리

**main의 `createGeminiClient`가 서 있는 전제(브라우저 직행 가능)가 프로브와 앱 코드 경로 양쪽에서 실측 확인됐다.** SPEC §12 미결 3의 Gemini 항목, 그리고 미결 5가 "잔여"로 표시한 *실키 BYO 실검증* 중 **CORS 부분이 해소된다**.

**단, "실키 BYO 실검증"이 전부 닫힌 것은 아니다.** 503으로 인해 루프가 라운드 0을 넘기지 못해(0/8, 상태 "대기") **실제 개선 곡선이 도는 것은 관측하지 못했다.** 닫힌 것은 "브라우저에서 벤더에 닿는가"이고, 남은 것은 "실키로 루프가 완주하는가"다.

## 프로토콜 정정 1건

PROTOCOL 초안(§3.3 / §5.3)에 "응답 헤더 중 CORS 관련 항목 표시"라고 적었으나 **이는 불가능하다.** 브라우저 명세상 자바스크립트는 `Access-Control-Allow-Origin` 등 CORS 응답 헤더를 읽을 수 없다(노출 목록에 없음).

따라서 판정은 헤더 관찰이 아니라 **성공/실패로 역산**한다:
- 상태 코드를 읽을 수 있다 = 브라우저가 응답을 통과시켰다 = **CORS 통과** (401·429여도 동일)
- `fetch`가 `TypeError`로 throw = 응답 자체가 차단됨 = **차단 의심** (정확한 사유는 브라우저 콘솔에만 기록됨)

프로브는 이 방식으로 구현했다. 이 정정은 결과를 보기 전에 확정된 것이 아니라 **구현 중 발견된 사실**이므로 판정 기준의 완화가 아님을 명시한다 — 오히려 판정 근거가 더 좁아졌다.

## 유효기간 (중요)

**이 결과에는 유효기간이 있다.** CORS 정책은 벤더가 예고 없이 바꿀 수 있으며, 특히 OpenAI는 브라우저 직행이 공식 문서화돼 있지 않아 **동작이 정책이 아니라 현재 상태일 뿐**이다. 출시 전 재확인이 필요하고, 제품에는 실행 전 연결 테스트(SPEC 미결 7)가 있어야 이 위험이 사용자에게 fail-fast로 드러난다.

## 관찰 — 응답 지연 차이

Gemini 973ms vs OpenAI 2588ms (각 1회, 최소 요청). 표본 1이라 성능 비교로 인용하지 말 것. 다만 루프가 라운드당 여러 콜을 하므로 **벤더 선택이 체감 속도에 영향을 준다**는 점은 UX 설계 시 고려 대상이다.

## 부수 관찰 — 체험 티어 모델의 가용성

앱 실행 시도에서 `gemini-3.7-flash`가 **연속 503(Service Unavailable)** 을 반환해 루프가 시작되지 못했다. 재시도(3회, 총 9초) 후에도 동일. 같은 날 오전 다른 실험에서는 같은 벤더의 다른 모델들이 **429(일일 무료 한도 20회 소진)** 로 막힌 바 있다.

**이는 코드 결함이 아니라 무료 티어의 운영 특성이다.** SPEC §12 미결 2가 체험 티어를 "최저가 모델"로 확정했으므로, 제품 관점에서 다음이 따라온다:

- 체험 사용자는 **429(한도)와 503(과부하) 양쪽에 노출**된다. 둘은 대처가 다르다 — 429는 기다려야 하고, 503은 재시도로 풀린다.
- 현재 앱은 둘을 구분하지 않고 "Gemini HTTP 5xx"로만 표시한다. 사용자가 "내일 와야 하나"를 판단할 수 없다.
- 체크포인트·재개는 정상 동작했다 — 오류 카드가 *"지금까지의 진행은 체크포인트에 저장되어 있습니다"* 를 안내하고 재시도 버튼을 제공한다. 이 부분은 설계대로다.

기록만 남기고 제안은 하지 않는다(표본 1일차).

## 부수 관찰 (실측 근거 확보됨 — 제안 가능)

PROTOCOL §7에 "실측 근거가 생겼을 때만 제안"으로 유보했던 항목:

**`createGeminiClient`의 재시도가 CORS 실패를 구분하지 않는다.** 현재 구현은 모든 실패를 3회 재시도하며 1.5s + 3s + 4.5s를 대기한다. 그러나 CORS 차단은 재시도로 풀리지 않는 종류의 실패다.

이번 실측에서 Gemini·OpenAI는 통과했으므로 **현재 이 경로가 실제로 발동하지는 않는다.** 다만 (a) 벤더가 정책을 바꾸는 경우 (b) 커스텀 endpoint(미결 7의 사용자 직접 입력) 도입 시에는 반드시 발생한다. 미결 7이 이미 요건으로 적어둔 *"실행 전 연결 테스트(1콜 ping)로 CORS·인증을 fail-fast"* 와 같은 문제의 두 측면이다.

제안 범위는 이 브랜치에서 결정하지 않고 기록만 남긴다.
