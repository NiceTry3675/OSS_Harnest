## 5분 버전 — 왜 이걸 했나

### 출발점의 의문

SPEC·PHILOSOPHY·interview_schema 세 문서는 아키텍처가 촘촘합니다. 그런데 읽다 보니 이 프로젝트가 서 있는 **두 개의 전제가 아직 아무도 실측하지 않은 상태**였습니다:

1. **반복이 원샷보다 실제로 나은가** — SPEC §3 원칙 6이 "델타 없는 템플릿은 채택하지 않는다"고 못 박았고, §12 미결 6은 이 실측이 **go/no-go 관문**이라고 명시. 그런데 측정된 적이 없음.
2. **그 점수를 믿을 수 있는가** — 검증 배터리(순서·변별력·안정성·꼼수 내성)가 설계돼 있지만 실행된 적 없음.

PHILOSOPHY의 첫 문장이 *"그럴듯함은 증거가 아니다"*인데, 정작 이 프로젝트 자체의 핵심 명제가 그럴듯함 상태로 남아 있었습니다. 그래서 재봤습니다.

### 어떤 순서로 무엇을 했나

**① 손으로 재기 (운영체제·정처기·컴활)**
자료 → AI에게 한 번만 요약 시킴(원샷) → 기출 6문제 채점 → 틀린 것 보고 3라운드 수정 → 재채점.
결과: 원샷 42~50점 → 반복 후 100점. 놓친 건 항상 "조건·예외"였음.
→ 전제가 맞는 것처럼 보였음.

**② 코드로 자동화 (Generator / Judge / 동결 / 오케스트레이터)**
실제 LLM API를 붙여 같은 절차를 코드로 재현. 여기서 "동결"을 실제로 구현 — 채점 프롬프트를 별도 파일로 빼고 SHA256 해시로 잠가서, 프롬프트를 고치면 실행이 즉시 에러로 막히게. 의도적으로 고치려면 해시를 재발급해야 함(= 스키마가 말하는 "재승인").
결과: **원샷부터 100점.** 손 실험과 정반대.

**③ 왜 다른가 — 가설 1: 형식 때문인가**
자동 생성된 요약본은 목록·콜아웃 구조였고 손으로 쓴 건 문단이었음. "구조화가 조건·예외를 더 잘 보존하는가?" 문단 강제 버전을 만들어 A/B 비교.
결과: 기본형 83점 vs 문단강제 92점 — 가설과 반대 방향.

**④ 잠깐, 이 비교 자체가 유효한가 — 안정성 확인**
같은 설정으로 3번 반복 실행.
결과: **83, 92, 100.** 같은 프롬프트·같은 모델인데 17점 폭으로 흔들림.
→ ③의 "83 vs 92" 비교는 **노이즈 폭 안에 들어가는 무의미한 비교**였음. 가설이 반박된 게 아니라 애초에 검증 불가능했음.
→ 그리고 더 중요한 것: **반복해도 항상 100점에 도달하지 않음**(2회차는 92에서 정체).

**⑤ 노이즈의 원인은 모델 등급인가**
한 단계 위 모델로 같은 3회 반복.
결과: **100, 100, 100. 노이즈 완전 소멸.**
→ 원인은 형식도 절차도 아닌 **모델 등급**이었음.

**⑥ 노이즈를 제대로 측정 (검증 배터리 "안정성" 검사 구현)**
지금까지의 83/92/100에는 생성 노이즈와 채점 노이즈가 섞여 있었음. **산출물 하나를 고정**하고 같은 저지로 5회 재채점해서 채점 노이즈만 분리.
결과: 약한 모델 σ=4.38 / 강한 모델 σ=0.00.
→ 그리고 예상 못 한 발견 두 개(아래 "결과물" 참조).

**⑦ 근본 반성 — 나는 지금 무엇을 개선하고 있는가**
여기서 멈추고 점검했더니 두 가지가 드러남:
- 지금까지 잰 건 전부 **루프 엔진**인데, 이 제품의 차별점은 루프가 아니라 **생성 엔진**(채점표를 만들어주는 것). PHILOSOPHY: *"동결 메커니즘은 흔하다. 동결할 평가자를 5분 만에 뽑아주는 것은 흔하지 않다."*
- 그리고 **채점 기준을 사람이 손으로 쓰고 있었음** = 제품의 심장을 하드코딩.
- 결정적으로, 과제 설계가 틀렸음: 원본 927자에 분량 제한 2200자 — **원본보다 2.4배 길게 써도 되는 "요약"**. 압축 압력이 0이라 버릴 이유가 없었고, 그래서 원샷이 만점 나온 것.

**⑧ 생성 엔진 구현**
자료 3021자 + 목표 + 분량 제한 900자(3.4배 압축)만 주고, **agent가 평가 문항 8개와 정답 키를 스스로 생성.**
→ 자료 전 범위에 고르게 분포, 압축 시 가장 먼저 버려질 디테일을 정확히 노림. 손으로 쓴 것보다 품질이 좋았음.

**⑨ 첫 실행 — 그런데 무효**
결과: 원샷 62점 → 최종 100점, 델타 +38. 오늘 처음으로 낮은 데서 출발해 올라감.
그런데 글자수가 900자 제한인데 1482 → 1939 → 2028 → **2158자**.
→ **내가 분량 검사를 구현 안 해서** 제한이 아무 효력이 없었음. 결과 전부 무효.

**⑩ hard gate 구현 (= 스펙 따라잡기)**
SPEC §3 원칙 4 / 스키마 v0.3 `evaluation.gates`에 이미 명세된 것을 구현. 소급 재판정하니 전 라운드 실격 — 유효한 후보가 애초에 없었음.
→ **이건 발견이 아니라 버그 수정입니다.** 위 "5번에 대한 정정" 참조.

## 결과물 — 팀에 쓸 수 있는 것

### A. 문서에 없는 발견 3가지

**1. 노이즈는 문항 유형에 집중된다.**
6문항 중 5개는 5회 재채점 내내 판정이 완전히 동일했고, 흔들린 1개만 **"비교·판단형"**(LRU가 FIFO보다 나은 근거)이었습니다. 나머지는 전부 사실 확인형.
→ 저지의 일반적 산만함이 아니라 **문항 유형에서 노이즈가 나온다**는 뜻. 생성 엔진이 루브릭을 만들 때 쓸 수 있는 구체적 지침이 됨. (단 n=1 관찰, 재현 필요)

**2. loser's curse — 문서에 없는 비대칭.**
어떤 산출물의 원래 기록 점수가 83점이었는데, 5회 재채점에서 **83이 한 번도 안 나왔습니다**(92 또는 100).
→ 즉 "83 → 100 개선 곡선"의 출발점이 저지가 유난히 짜게 준 한 번이었을 가능성.
→ 문서는 채택 후 챔피언 재채점으로 winner's curse를 막습니다(SPEC §5.1.1 채택 규칙 2). 그런데 **베이스라인 쪽에는 대칭적 방어가 없습니다.** 베이스라인은 델타의 분모, 즉 제품이 사용자에게 보여주는 유일한 증거의 기준점입니다.
→ **제안**: 원샷 베이스라인만큼은 여러 번 채점해 중앙값을 쓰는 것을 검토. 비용은 라운드 0에 국한(라운드당이 아님).

**3. 티어 리스크가 양방향이다.**
| | 무료(최저가 모델) | BYO(강한 모델) |
|---|---|---|
| 저지 노이즈 | σ≈4.4, 판정 뒤집힘 | σ=0 |
| 원샷 델타 | 나옴 | 0 (원샷부터 만점) |
| 리스크 | 노이즈를 개선으로 착각 | 루프가 무의미해 보임 |

→ §12 미결 6은 "강한 모델로 통과한 델타가 체험 경로에서 재현 안 되는" 방향만 경고합니다. **반대 방향(체험 티어 델타가 BYO에서 사라지는 것)은 문서에 없습니다.** 돈 내는 사용자에게 루프가 가장 무의미해 보일 수 있다는 뜻.

### B. 동작하는 코드 (`experiments/sandbox/`)

| 파일 | 역할 |
|---|---|
| `rubric_maker.py` | **생성 엔진** — 자료로부터 평가 문항·정답키 생성 |
| `judge.py` + `judge_prompt.frozen.txt/.sha256` | 저지 + **해시로 잠근 동결** + **hard gate** |

### C. 구현 정합성 (발견 아님, 기록용)

hard gate를 구현했습니다(`judge.check_gates()`). 문서에 이미 명세된 것을 따라잡은 것이며 새로운 통찰이 아닙니다. 설계 결정만 기록해둡니다:

- 분량은 **결정적으로만** 검사 — `len()`이면 되는 걸 LLM에게 맡기면 그 자체가 노이즈원이 됨
- reject 게이트 위반 시 LLM 채점 자체를 생략 — API 호출 절약 + "실격인데 88점" 같은 혼란 제거
- 모르는 scorer는 조용히 통과시키지 않고 실패 처리 — 게이트가 있다고 착각하게 만드는 게 없는 것보다 나쁨

## 정직한 평가 — 돌아온 부분

가장 값싼 경로는 **⑦(근본 반성) → ⑧(생성 엔진)**으로 바로 가는 것이었습니다. ①~⑥이 다 필요했냐면 아닙니다.

**낭비였던 것**: ③의 형식 가설 추적(표본이 부족한 상태에서 A/B를 해석하려 함), 파이썬 경로·인코딩·모델 폐기·할당량 같은 환경 디버깅.

**낭비가 아니었던 것**: ④~⑥의 노이즈 측정. 이게 없었으면 ⑨의 "델타 +38"을 **성공으로 기록했을 것**입니다. 숫자를 의심하는 습관과 기준선이 거기서 생겼습니다. 그리고 그 과정에서 나온 발견 3개는 문서에 없는 내용입니다.

**교훈**: 결과가 나올 때마다 그 원인을 파고들기 전에, **"지금 개선하려는 대상이 무엇인가"**를 먼저 물어야 했습니다. ①~⑥은 개선 대상이 없는 상태에서 측정만 한 구간입니다.
