# 비개발자 관점 용어 및 표현 점검 목록

이 문서는 Harnest의 문서와 프런트 화면에서 발견한 표현 중 다음에 해당하는 항목을 모은 점검 목록이다.

- 무엇을 가리키는지 바로 알기 어려운 표현
- 같은 대상을 서로 다른 이름으로 부르는 표현
- 개발·통계·AI 분야 지식이 있어야 이해하기 쉬운 표현
- 주체, 대상, 입력 위치 또는 결과가 생략된 표현
- 실제 동작보다 강하거나 다른 인상을 줄 수 있는 표현
- 특정 템플릿의 용어가 Harnest 전체의 공통 개념처럼 사용된 표현

이 문서는 **교체 후보를 모으는 조사 문서**다. 제품 정책이나 계약을 변경하지 않는다. 아래의 개별 `권장 방향`은 최초 수집안이고, 실제 문장과 계약상의 역할을 다시 대조한 결과는 §2의 `문맥 검증 결과`와 `검증된 교체 용어안`에 정리했다. 실제 교체 시에는 [`SPEC.md`](../SPEC.md)의 의미와 `packages/contracts`의 계약을 유지해야 한다.

## 1. 조사 범위와 읽는 법

### 조사 범위

| 구분 | 확인한 범위 | 이 문서에서의 취급 |
|---|---|---|
| 현재 제품 설명 | `README.md`, `SPEC.md`, `PHILOSOPHY.md`, `ROADMAP.md`, `CONTRIBUTING.md`, `docs/user-scenario.md` | 현재 의미를 정하거나 사용자 관점에서 풀어 쓴 문서로 취급 |
| 프런트 화면 | `apps/web/src/pages`, `apps/web/src/components`, `apps/web/src/templates.tsx`, 각 템플릿의 사용자 노출 문구 | 가장 높은 교체 우선순위 |
| 계약·엔진 | `packages/contracts`, `packages/loop-engine`의 타입, 오류 문구, 테스트 설명 | 내부 식별자는 유지할 수 있으나 사용자 노출 문구는 점검 대상 |
| 설치·운영 | `apps/api/README.md`와 루트 README의 모델 연결·저장 설명 | 일반 사용자 설명과 개발자 설명을 분리할 필요가 있음 |

`experiments/`의 실험 기록·원자료와 `docs/archive/`의 보관 문서는 현재 제품 문안이 아니므로 조사, 용어 수집, 교체안 작성과 출처 근거에서 모두 제외한다.

### 프로젝트 핵심과 템플릿 경계

Harnest를 관통하는 핵심은 특정 종류의 결과물을 만드는 일이 아니다.

> 사용자가 좋은 결과를 판단할 평가 기준과 전체 평가 구성을 확인하고 승인하면, Harnest는 실행 중 그 구성을 바꾸지 않고 새 개선안을 같은 구성으로 비교하며, 채택 과정과 결과 근거를 남긴다.

따라서 공통 제품 언어는 다음 흐름을 설명해야 한다.

1. 사용자가 **결과물**과 작업에 필요한 입력을 제공한다.
2. Harnest가 **평가 기준·필수 조건·채점 방식**을 포함한 평가 구성을 만든다.
3. 사용자가 **평가 구성을 승인·확정**하고, Harnest가 실행하는 동안 같은 구성을 **적용**한다.
4. Harnest가 **최초 결과물**과 **새 개선안**을 같은 평가 구성으로 채점한다.
5. 필수 조건과 채택 조건을 만족한 개선안만 **현재 결과물**로 남긴다.
6. Harnest가 점수 변화, 채택하지 않은 개선안, 종료 사유와 적용된 확인 방법을 기록한다.

결과물의 형태, 입력 항목, 평가 사례의 구조와 표시 방식은 템플릿이 정한다. `인수인계 문서`, `실제로 받았던 질문과 답`, `답변력`, `커버리지`는 현재 인수인계 템플릿의 언어이지 Harnest 전체의 언어가 아니다. 시간표 역시 개발용 템플릿일 뿐 프로젝트 전체를 대표하지 않는다.

### 표의 기준

- **높음**: 주요 흐름에서 사용자가 직접 보고 행동을 결정하는 표현
- **중간**: 상세 설명, 결과 화면 또는 핵심 문서에서 이해를 방해하는 표현
- **낮음**: 개발·운영·실험 문맥에서는 쓸 수 있지만 일반 사용자 문맥과 분리해야 하는 표현
- **권장 방향**: 뜻을 보존하면서 쉬운 말로 바꿀 때의 방향이며, 최종 UI 문안은 별도로 결정한다.
- **출처**: 같은 표현이 많은 곳에 반복될 때에는 대표적인 위치를 적었다.
- **표어·브랜드 문구 제외**: 홈 헤드라인, 브랜드 비유, 짧은 애니메이션 문구와 대화형 섹션 제목은 이 용어 교체 후보 목록에 넣지 않는다. 같은 표현이 입력·승인·오류·결과 같은 기능 문구에 쓰일 때만 그 기능 문맥을 별도로 점검한다.

## 2. 먼저 통일해야 할 핵심 개념

최초 수집 때에는 아래 표현을 같은 개념의 충돌 후보로 묶었다. 2026-08-26에 실제 사용자 문장, 핵심 문서의 정의, 계약 타입과 실행 흐름을 다시 대조했다. 검증 결과, **완전히 같은 뜻인 묶음은 일부뿐이며 나머지는 상위·하위 개념 또는 서로 다른 상태와 행위**였다. 따라서 문자열 전체 일괄 치환은 적합하지 않다.

검증은 다음 기준으로 완료했다.

1. 현재 브랜치의 핵심 문서와 프런트 운영 소스에서 각 표현의 앞뒤 문장을 확인했다.
2. 화면 문구만으로 뜻을 확정하지 않고 `packages/contracts`, `packages/loop-engine`, 템플릿 런타임에서 해당 값이 생성·사용되는 역할을 대조했다.
3. 비슷한 표현이 실제로 같은 값이나 단계를 가리키는지, 상하위 개념인지, 서로 다른 행위인지 구분했다.
4. §2.3의 현재 문구 31개가 모두 실제 프런트 소스에 존재하는 것을 고정 문자열로 재확인했다.
5. `experiments/`와 `docs/archive/`는 문맥 비교에도 사용하지 않고 조사 범위에서 제외했다.

### 2.2 검증된 교체 용어안

아래 표는 실제 교체 작업에서 사용할 수 있는 **사용자 노출용 1차 용어안**이다. `내부 용어`는 코드 식별자와 개발자용 계약에서 그대로 유지해도 된다. 한 행의 용어를 다른 행의 용어와 합치지 않는 것이 중요하다.

#### 결과물과 개선 상태

| 내부·현재 용어 | 사용자 노출용 교체안 | 이 용어를 쓰는 문맥 | 구분해야 할 표현 |
|---|---|---|---|
| artifact / 산출물 / 일반적인 결과물 | **결과물** | 작업 유형과 무관하게 사용자가 만들거나 개선하려는 대상 | 인수인계 작업에서 결과물 종류를 말할 때는 `인수인계 문서` |
| document / 문서 | **인수인계 문서** | 인수인계·온보딩 작업의 결과물 | 모든 템플릿의 공통 대상을 `문서`로 부르지 않음 |
| candidate / 후보 / 수정본 | **새 개선안** | 한 개선 회차에서 새로 만들어 비교하는 결과물 | 아직 채택되지 않았으므로 `새 결과물`로 단정하지 않음 |
| champion / 챔피언 / 최선본 | **현재 결과물** | 지금 유지되어 다음 개선의 출발점이 되는 결과물 | 현실의 절대적 최선이라는 뜻의 `최고 결과물`은 피함 |
| final artifact / 최종 최선본 | **최종 결과물** | 실행이 끝났을 때 남은 현재 결과물 | 최초 결과물과 구분 |
| one-shot artifact / 원샷 산출물 / 라운드 0 결과 | **최초 결과물** | 실행을 시작하기 전에 한 번 만든 결과물 | 비교 역할을 말할 때는 `최초 점수` |
| baseline score / 기준선 점수 | **최초 점수** | 이후 개선 점수와 비교하는 시작 점수 | 생성 방식을 뜻하는 `원샷`과 구분 |

#### 평가와 승인

| 내부·현재 용어 | 사용자 노출용 교체안 | 이 용어를 쓰는 문맥 | 구분해야 할 표현 |
|---|---|---|---|
| evaluation procedure / 판정 절차 / 평가 절차 / 평가 방법 | **평가 구성** | 사용자가 한 번에 검토·승인하는 기준, 필수 조건, 채점 방식, 질문 사용법 전체 | 개별 `평가 기준`과 구분 |
| criterion / criteria / 채점 기준 | **평가 기준** | 결과물의 어떤 품질을 점수에 반영하는지 설명 | 필수 조건과 구분 |
| gate / hard gate / 게이트 | **필수 조건** | 지키지 않으면 점수 비교 전에 제외되는 조건 | 가중 점수를 주는 평가 기준과 구분 |
| scoring / score | **채점 / 점수** | 결과물에 기준을 적용해 숫자를 계산 | 채택 여부 결정과 구분 |
| scalar / total / aggregate | **종합 점수** | 여러 평가 기준의 점수를 하나로 합친 값 | 질문 하나의 점수와 구분 |
| adoption decision / 판정 | **채택 결정** | 새 개선안을 현재 결과물로 바꿀지 결정 | 채점 자체와 구분 |
| approve | **평가 구성 승인** | 사용자가 실행 전에 평가 구성 전체에 동의 | 결과물 채택과 구분 |
| lock / freeze / 동결 | **승인한 평가 구성 유지** | AI가 결과물을 만들고 평가하는 동안 평가 구성을 바꾸지 못하게 하는 상태 | 사용자가 영구히 수정할 수 없다는 뜻이 아님 |
| Evaluation Pack / Pack | **평가 규칙 묶음** | 사용자 입력으로 구성되어 승인 대상이 되는 내부 데이터 구조 | 승인 전에도 존재하므로 승인 뒤의 상태만 `승인된 평가 규칙 묶음`이라고 부름. 코드와 개발 문서에서는 `Evaluation Pack` 유지 가능 |
| definitionDigest / digest / 기준 지문 | **평가 구성 확인 코드** | 저장 기록과 현재 승인 내용이 같은지 확인하는 코드 | 비밀번호나 보안 인증 코드로 설명하지 않음 |
| examiner / examiner report / 시험관 검증 | **AI 평가 사전 점검 / AI 평가 사전 점검 결과** | 승인 전에 선택한 AI의 평가 안정성과 속임수 내성을 확인 | 모델 선택과 결과물을 평가하는 본 실행을 구분 |
| judge / judge model / 저지 모델 / 채점 모델 / 채점 AI / 결과물 평가 AI | **사용할 AI 모델** | 현재 실행에서 결과물 생성과 평가에 함께 사용하는 AI 모델 | 내부 계약의 `judge` 식별자는 유지 |
| deterministic scorer / 결정적 채점 | **정해진 규칙으로 채점** | AI 판단 없이 같은 입력에 같은 점수를 계산 | `확실한`, `오류가 없는`이라는 뜻으로 확대하지 않음 |
| pairwise | **개선안 채택 조건** | 새 개선안을 현재 결과 대신 남기는 조건 | 일반 사용자 화면에서는 미적용 기술을 설명하지 않고 실제 채택 조건만 표시한다. 내부 계약과 개발 문서의 `pairwise`는 유지한다. |

#### 선택형 평가 사례 — 공통 개념과 인수인계 템플릿 표시 구분

평가 사례, 중간 점검, 최종 확인은 모든 템플릿에 필수인 흐름이 아니다. 템플릿이 해당 기능을 구성한 경우에만 표시한다. 질문과 답으로 사례를 만드는 방식은 현재 인수인계 템플릿에 한정된다.

| 내부·현재 용어 | 공통 제품 문서 | 인수인계 템플릿 화면 | 범위와 설명 |
|---|---|---|---|
| case / 케이스 | **평가 사례** | **질문·답변 사례** | 사례의 실제 구조는 템플릿이 정함 |
| visible case / feedback case / 가시 케이스 | **개선에 사용하는 평가 사례** | **개선에 사용하는 질문** | 상세 평가 결과가 다음 개선에 사용되는 경우 |
| guard case / validation guard / 중간 점검 | **중간 점검에 쓰는 평가 사례** | **중간 점검 질문** | 구성된 경우에만 사용하며, 합계만 채택 결정에 반영. 처음에는 `개선안이 기존 결과보다 크게 나빠지지 않았는지 확인`한다고 설명 |
| guard score / 가드 집계 | **중간 점검 점수** | **중간 점검 점수** | 새 개선안이 현재 결과보다 허용 범위를 넘게 나빠졌는지 비교하는 집계 값 |
| holdout case / 홀드아웃 / 숨긴 질문 | **최종 확인용 평가 사례** | **최종 확인용 질문** | 구성된 경우 최초와 종료 시점에만 채점하고 개선 과정에는 공개하지 않음 |
| holdout score | **최종 확인 점수** | **최종 확인 점수** | 채택·생성·중단에는 사용하지 않음 |
| case provenance / 케이스 출처 | **평가 사례의 입력 출처** | **질문·답변 사례의 작성 방식** | 구체적인 출처 종류와 표시는 템플릿이 정함 |

#### 반복 실행과 결정 결과

| 내부·현재 용어 | 사용자 노출용 교체안 | 이 용어를 쓰는 문맥 | 사용자에게 보여줄 완전한 상태 문구 |
|---|---|---|---|
| loop / 루프 | **실행** | 새 개선안을 만들고 평가하는 전체 과정 | `실행 시작`, `실행 완료` |
| round / 라운드 | **개선 N회차** | 새 개선안 한 개를 만들고 비교하는 단위 | 최초 결과는 회차 수에 넣지 않고 `개선 시작 전`으로 표시 가능 |
| checkpoint / 체크포인트 | **저장된 진행 상태** | 일시정지, 새로고침, 재개에 필요한 상태 | `현재 개선 회차가 끝난 뒤 진행 상태를 저장함` |
| adopted | **새 개선안 채택** | 필수 조건과 중간 점검을 통과하고 종합 점수가 더 높음 | `종합 점수가 더 높아 새 개선안으로 교체했습니다.` |
| gate rejected / 탈락 / 실격 | **필수 조건 위반으로 제외** | 점수 비교 전에 새 개선안을 제외 | `필수 조건을 지키지 않아 새 개선안을 제외했습니다.` |
| guard rejected | **중간 점검 점수 기준 미달** | 새 개선안의 중간 점검 점수가 허용 범위보다 낮음 | `새 개선안의 중간 점검 점수가 허용 범위보다 낮아 현재 결과물을 유지했습니다.` |
| score not improved / 미채택 | **점수가 오르지 않아 기존 결과 유지** | 새 개선안의 종합 점수가 현재 결과보다 높지 않음 | 동점도 이 문구에 포함됨을 상세 설명에서 표시 |
| rejected / 기각 | **채택하지 않음** | 실패 원인을 아직 특정하지 않는 포괄 상태에만 사용 | 가능하면 위 세 원인별 문구를 우선 사용 |
| plateau | **N회 연속 개선 없음** | 정해진 횟수만큼 새 개선안이 채택되지 않아 종료 | `N회 연속 더 나은 개선안이 없어 실행을 마쳤습니다.` |
| ceiling | **최고 점수 도달** | 종합 점수 100점에 도달해 더 높은 점수가 불가능 | `최고 점수에 도달해 실행을 마쳤습니다.` |
| max rounds | **설정한 개선 횟수 완료** | 최대 개선 회차를 모두 사용해 종료 | `설정한 N회의 개선을 모두 진행했습니다.` |
| curve / 챔피언 곡선 | **채택 결과의 점수 변화** | 회차별 새 개선안 점수가 아니라 채택 후 남은 점수의 변화 | 차트 설명에 `채택되지 않은 개선안은 선에 반영되지 않음` 표시 |
| round record / 시도한 기록 | **개선안 비교 기록** | 회차별 새 개선안 점수, 현재 결과 점수, 채택 여부와 이유 | 질문별 채점 결과와 구분 |
| trace / violations / 판정 사유 | **평가 항목별 채점 결과** | 개선에 사용하는 항목별 점수와 공개 가능한 평가 이유 | 템플릿이 질문 사례를 쓸 때에만 `질문별 채점 결과`라고 표시 |
| checkpoint provenance / 실행 provenance | **실행 상태 변경 기록** | 시작, 개선 회차, 채택, 일시정지, 재개, 종료 사건 | 질문·답변 사례의 작성 방식과 구분 |
| inference live / 추론 실황 | **AI 작업 기록** | 공개된 추론 요약과 채점 이유의 스트림 | `AI의 전체 내부 사고 과정`이라고 표현하지 않음 |

#### 모델 연결과 저장

| 내부·현재 용어 | 사용자 노출용 교체안 | 이 용어를 쓰는 문맥 | 구분해야 할 표현 |
|---|---|---|---|
| vendor / provider / 공급자 / 프로바이더 | **AI 연결 대상** | OpenAI, Gemini, Vertex AI, OpenRouter 또는 내 컴퓨터의 Ollama 선택 | 외부 서비스와 로컬 프로그램을 모두 `회사`나 `외부 서비스`라고 부르지 않음 |
| credentials / 자격 증명 | **AI 연결 정보** | 여러 종류의 연결 값을 포괄하는 제목 | 실제 입력 칸에서는 구체적 형식을 표시 |
| API key | **API 키** | OpenAI·Gemini·Anthropic·OpenRouter 연결 값 | 낯선 사용자에게는 발급처 도움말 필요 |
| Vertex service account JSON | **Vertex AI 서비스 계정 JSON** | Vertex AI 연결에 사용하는 JSON 내용 또는 파일 | API 키라고 부르지 않음 |
| localStorage | **이 브라우저의 저장 공간** | 키가 Harnest 서버가 아닌 현재 브라우저에 남는 위치 | 계정 전체나 컴퓨터 전체 저장으로 확대하지 않음 |
| direct vendor request / 벤더 직행 | **브라우저에서 선택한 AI 연결 대상으로 직접 전송** | Harnest 서버를 거치지 않는 기본 모델 요청 | 공유 키 경로는 예외이므로 별도 설명 |
| model call / 모델 호출 | **AI 요청** | 요청 횟수와 비용을 설명 | 한 번의 사용자 클릭과 요청 횟수가 같다고 가정하지 않음 |
| export artifact / 문서 내려받기 | **결과물 파일 저장** | 최종 결과물 하나를 사람이 여는 형식으로 저장 | 전체 실행 기록과 구분 |
| project export / JSON 내보내기 | **전체 실행 기록 저장 (.json)** | 승인 내용, 진행, 점수를 JSON 파일로 저장 | 결과물 파일과 구분 |
| persist / 서버에 기록 | **Harnest 서버에 저장** | 사용자가 명시적으로 프로젝트와 결과 저장을 선택 | 기본적으로 자동 저장된다고 표현하지 않음 |
| optional backend | **선택형 저장 서버** | 서버 저장 기능을 제공하는 선택 구성 | 평가와 AI 요청을 대신 실행하지 않음 |

### 2.3 실제 문장에 적용할 수 있는 교체안

아래 문장은 앞뒤 문맥과 실제 동작을 확인한 뒤 작성한 1차 교체안이다. `위치`에서 인수인계 템플릿 범위를 명시한 문구는 그 템플릿 안에서만 교체하며 공통 제품 용어로 올리지 않는다. 표어·브랜드 문구는 이 표에서 제외했다. 아직 원본 프런트와 문서에는 반영하지 않는다.

|---|---|---|---|
| 홈 | `채점 기준을 검토하고 승인하면 잠깁니다.` | **평가 구성을 승인하면 이번 실행이 끝날 때까지 바뀌지 않습니다. 바꾸려면 수정 후 다시 승인해야 합니다.** | 기준뿐 아니라 필수 조건·채점 방식과 템플릿이 구성한 평가 사례 사용법까지 digest 범위에 포함됨 |

| 인수인계 템플릿 입력 | `AI 초안 N개 넣기` | **질문·답변 사례 칸에 AI 초안 N개 추가** | 생성 결과가 case list에 들어가며 사용자 확인 전에는 제출되지 않음 |

| 인수인계 템플릿 승인 | `꼼수에 속지 않는가` | **사실을 꾸미거나 칭찬만 하는 답에 높은 점수를 주지 않는가** | 현재 인수인계 템플릿의 날조·아첨 시험 응답 처리를 검사함 |
| 인수인계 템플릿 승인 | `질문 나누기` | **질문·답변 사례의 사용 목적** | 이 템플릿의 사례를 개선·중간 점검·최종 확인에 각각 사용하도록 분할함 |
| 승인 | `승인하고 잠그기` | **이 평가 구성 승인** | 승인 후 해당 digest의 평가 구성으로만 실행 가능함 |

### 2.4 1차 통일 기준 — 기능을 전달하는 비유적 표현

이번 1차 통일은 문서와 프런트에서 사용자가 실제 기능을 이해하는 데 영향을 주는 **비유적 표현**을 명확한 기능 용어로 바꾸는 데 목적이 있다. 브랜드명, 표어, 홈 화면의 인상적 문구는 포함하지 않는다. 또한 화면 흐름, 컴포넌트 구조, 기능 정책을 바꾸는 작업이 아니므로 다음 원칙을 적용한다.

1. **쉽게 쓴다는 이유로 길게 풀어쓰지 않는다.** 원문의 정보 밀도와 화면 리듬을 유지하면서 낯선 비유와 전문어만 걷어낸다.
2. **같은 정책도 화면의 역할에 맞춰 표현한다.** 결정 단계는 `기준 확정`, 실행 상태는 `평가 구성 적용 중`, 정책 설명은 `AI가 결과물을 만들고 평가하는 동안 바뀌지 않음`으로 구분한다.
3. **라벨·배지·버튼·목록 상태는 원문과 비슷한 길이를 유지한다.** 긴 설명은 사용자의 행동에 꼭 필요한 경우에만 도움말이나 오류 본문에서 한 번 제공한다.
4. **이미 화면 문맥으로 드러난 주체와 대상을 반복하지 않는다.** 제목이 `평가 구성 승인`이면 바로 아래에서 `사용자가 아래 평가 구성을 승인합니다`처럼 같은 내용을 되풀이하지 않는다.
5. **버튼은 상태명이 아니라 사용자의 행동을 적는다.** 사용자는 평가 구성을 `승인`하고, 시스템은 실행 중 승인된 평가 구성을 `적용`한다. 실행 제어 버튼은 `시작`, `일시정지`, `재개`처럼 짧게 쓴다.
6. **대표 용어를 모든 문맥에 1대1로 치환하지 않는다.** 단계는 `중간 점검`, 측정값은 `중간 점검 점수`, 실패 상태는 `중간 점검 점수 기준 미달`처럼 그 자리에서 가리키는 대상을 명시한다.
7. **코드 식별자와 계약은 바꾸지 않는다.** `candidate`, `champion`, `checkpoint`, `definitionDigest` 등은 내부 이름으로 유지하고 사용자에게 보이는 문구만 아래 대표어에 맞춘다.
8. **템플릿이 정하는 대상명은 공통어로 덮지 않는다.** 공통 문서의 `평가 사례`는 인수인계 화면에서 `질문·답변 사례`로 표시할 수 있다.

#### 통일할 대표 용어

| 현재 비유·혼용 표현 | 통일할 대표 용어 | 짧은 화면형 | 적용 범위와 사용 규칙 |
|---|---|---|---|
| 판정 절차 / 평가 절차 / 평가 방법 | **평가 구성** | `평가 구성` | 사용자가 평가 기준, 필수 조건, 채점 방식 등을 함께 검토·승인하는 대상을 가리킨다. 개별 항목과 가중치는 `평가 기준`, 점수 계산은 `채점`, 개선안 유지 여부는 `채택 결정`으로 따로 쓴다. |
| 잠금 / 잠김 / 동결 / 봉인 / 불가침 | **평가 구성 확정·적용** | 단계 `기준 확정`, 실행 상태 `평가 구성 적용 중` | 사용자가 평가 구성을 승인해 결정을 마친 단계와, 실행에 같은 구성을 사용하는 상태를 구분한다. 바뀌지 않는다는 정책은 `AI가 결과물을 만들고 평가하는 동안 승인한 평가 구성은 바뀌지 않습니다`로 설명한다. |
| 시험관 / 시험관 검증 / 시험관 배터리 | **AI 평가 사전 점검** | `사전 점검` | 결과물을 개선하기 전에 선택한 AI의 평가 안정성과 속임수 내성을 확인하는 절차다. 결과 명칭은 `AI 평가 사전 점검 결과`로 쓴다. |
| 저지 / 저지 모델 / 채점 모델 / 채점 AI / 결과물 평가 AI | **사용할 AI 모델** | `AI 모델` | 현재 실행에서 결과물 생성과 평가에 함께 사용하는 모델을 가리킨다. 역할을 설명할 때는 `결과물 생성`과 `AI 평가`로 나눠 쓴다. |
| 기준 지문 / 다이제스트 | **평가 구성 확인 코드** | `확인 코드` | 저장 기록과 현재 평가 구성이 같은지 확인하는 값이다. 비밀번호나 보안 인증 수단처럼 설명하지 않는다. 개발 문서의 `definitionDigest`는 유지한다. |
| 게이트 / hard gate / 관문 | **필수 조건** | `필수 조건` | 지키지 않으면 점수 비교 전에 제외되는 조건이다. 결과 상태는 `필수 조건 위반`으로 표시한다. |
| 후보 / candidate | **새 개선안** | `개선안` | 한 개선 회차에서 새로 만들어 현재 결과물과 비교하는 대상이다. 채택되기 전이므로 `새 결과물`로 단정하지 않는다. |
| 챔피언 / 최선본 / champion | **현재 결과물** | `현재 결과` | 현재 유지되며 다음 개선의 출발점이 되는 대상이다. 절대적인 최선이라는 뜻의 `최고 결과물`은 쓰지 않는다. |
| 라운드 / round | **개선 회차** | `N회차` | 새 개선안 하나를 만들고 비교하는 반복 단위다. 문서에서는 `개선 N회차`, 좁은 목록·차트에서는 `N회차`, 누계는 `총 N회 개선`으로 쓴다. |
| 루프 / loop | **실행** | `실행` | 사용자에게 보이는 전체 과정의 단계명이다. 한 번의 시도인 `개선 회차`와 구분하며 내부 식별자 `loop`는 유지한다. |
| 관제실 | **실행** | 화면명 `실행`, 상태 `개선 중…` | 단계와 화면 제목은 `실행`으로 통일한다. 홈의 서비스 분류는 `AI 결과물 생성·평가`, 현재 상태는 `개선 준비·개선 중·개선 일시정지·개선 완료`로 구분한다. |
| 체크포인트 / checkpoint | **저장된 진행 상태** | `진행 저장` | 일시정지·새로고침·재개에 필요한 상태다. 문장에서는 `현재 진행 상태를 저장했습니다`처럼 실제 동작을 적는다. |
| 가드 / validation guard | **중간 점검** | `중간 점검` | 구성된 경우 새 개선안이 현재 결과보다 허용 범위를 넘게 나빠지는지 확인하는 장치다. 첫 설명에서만 목적을 풀어 쓰고 이후에는 짧은 단계명을 유지한다. `품질 유지 확인`은 더 추상적이라는 사용자 검토에 따라 폐기했다. |
| 홀드아웃 / holdout / 숨김 세트 | **최종 확인** | `최종 확인` | 구성된 경우 개선 과정에는 사용하지 않고 최초와 종료 시점에만 평가하는 장치다. 사례를 가리킬 때는 공통 문서에서 `최종 확인용 평가 사례`, 인수인계 화면에서 `최종 확인용 질문`으로 쓴다. |
| 방어 세트 / 활성 방어 세트 | **품질 보호 규칙** | `적용된 보호 규칙` | 필수 조건, 중간 점검, 최종 확인과 적용 제외 사항을 결과 화면에서 묶어 보여줄 때 쓴다. 보안 기능으로 오해될 수 있는 `방어`는 쓰지 않는다. |
| 추론 실황 | **AI 작업 기록** | `AI 작업 기록` | 사용자에게 공개된 작업 요약과 채점 이유를 보여주는 영역이다. AI의 전체 내부 사고 과정이라고 표현하지 않는다. |
| 스칼라 / scalar / 합계 점수 | **종합 점수** | `종합 점수` | 여러 기준의 점수를 하나로 합쳐 개선안 채택에 사용하는 값이다. 개별 평가 항목 점수와 구분한다. |

#### 일괄 치환하지 않을 표현

다음 묶음은 비슷해 보여도 실제 동작이 달라 한 단어로 통일하지 않는다. 용어 통일 작업에서도 문맥에 맞는 표현을 선택한다.

| 혼용되기 쉬운 묶음 | 유지할 구분 |
|---|---|
| 승인 / 확정 / 적용 | 사용자는 `평가 구성을 승인`하고, 화면은 결정이 끝난 단계를 `기준 확정`으로 표시한다. 실행 화면에서는 시스템 상태를 `평가 구성 적용 중`으로 표시한다. |
| 기준 / 구성 / 채점 / 채택 / 점검 | 항목과 가중치는 `평가 기준`, 승인 대상 전체는 `평가 구성`, 숫자 계산은 `채점`, 개선안 유지 여부는 `채택 결정`, 선택한 AI의 평가 검사는 `사전 점검`, 개선 종료 후 성능 확인은 `최종 확인`이다. |
| 최초 결과물 / 최초 점수 / 개선 시작 전 | 각각 대상, 비교 점수, 시점을 뜻한다. `원샷·베이스라인·라운드 0`을 한 표현으로 기계적으로 바꾸지 않는다. |
| 필수 조건 위반 / 중간 점검 점수 기준 미달 / 점수 미개선 | 목록 상태는 `필수 조건 위반`, `중간 점검 점수 기준 미달`, `점수 개선 없음`으로 쓴다. 상세 설명에서는 각각 제외·유지 이유를 한 문장으로 밝힌다. |
| 결과물 / 새 개선안 / 현재 결과물 | `결과물`은 공통 대상, `새 개선안`과 `현재 결과물`은 개선 회차 안의 서로 다른 상태다. |
| 평가 사례 / 질문·답변 사례 | 공통 개념은 `평가 사례`, 현재 인수인계 템플릿의 실제 입력·표시 대상은 `질문·답변 사례`다. |
| 저장된 진행 상태 / 전체 실행 기록 / 결과물 파일 | 재개용 상태, 기록용 JSON, 사람이 사용하는 최종 파일은 서로 다른 저장 대상이다. |

## 3. 프런트 화면에서 발견한 표현

프런트 페이지는 공통 실행 흐름을 조립하지만, 일부 문구는 선택한 템플릿이 제공하거나 현재 인수인계 설정을 표시한다. 아래에서 질문·답변·문서·분량·커버리지에 관한 항목은 **인수인계 템플릿 전용 후보**이며 Harnest 공통 용어가 아니다.

## 6. 교체 작업에서 지켜야 할 경계

1. **사용자 화면은 내부 식별자보다 행동과 대상을 먼저 말한다.** 예를 들어 `definitionDigest 불일치`보다 `저장된 진행 기록과 현재 승인한 평가 구성이 다름`을 먼저 보여준다.
2. **주체와 대상을 생략하지 않는다.** `숨긴 사례`는 `결과물을 만드는 AI에 공개하지 않는 최종 확인용 평가 사례`처럼 누구에게 숨기고 어디에 쓰는지 설명한다. 템플릿 화면에서는 실제 사례 형태에 맞는 이름을 쓴다.
3. **서로 다른 실패 원인을 같은 말로 뭉개지 않는다.** 필수 조건 위반, 중간 점검 점수 기준 미달, 점수 미개선은 각각 다른 결과 문구가 필요하다.
4. **기능 설명과 실행 결과는 동작보다 강하게 말하지 않는다.** `눈에 보이는 질문에만 맞췄습니다`처럼 관측하지 않은 원인을 단정하지 않는다.
5. **내부 계약 이름은 무리하게 번역하지 않는다.** 코드의 `definitionDigest`, `holdoutPolicy`, `checkpoint`, `provenance` 같은 식별자는 유지하고, 화면과 일반 문서에 쉬운 표시 이름을 매핑한다.
6. **기술 상세는 없애지 말고 층을 나눈다.** API 키 저장, JWT 서명, CORS, JSON 형식은 필요한 정보다. 기본 설명에는 사용자가 해야 할 행동과 데이터 이동을 적고, 구현 상세는 개발자용 절로 보낸다.
7. **실험·보관 자료는 용어 조사에서 제외한다.** `experiments/`와 `docs/archive/`에만 있는 표현은 수집하거나 현재 제품 문안의 교체 근거로 사용하지 않는다.
8. **공통 대표어와 템플릿 대표어를 분리한다.** `결과물`, `평가 구성`, `평가 기준`, `필수 조건`, `새 개선안`, `현재 결과물`, `개선 회차`는 프로젝트 공통 언어로 통일한다. `질문·답변 사례`, `인수인계 문서`, `답변력`, `커버리지`는 인수인계 템플릿 안에서만 통일한다.
9. **표어·브랜드 문구는 후보 목록에서 제외한다.** 홈 헤드라인, 브랜드 비유, 짧은 애니메이션 문구와 대화형 섹션 제목은 수집하지 않는다. 입력 라벨, 행동 대상이 불분명한 버튼, 승인 내용, 실행 상태, 오류와 결과 설명만 기능 문구로 점검한다.
10. **템플릿 하나를 프로젝트 전체로 일반화하지 않는다.** 공통 페이지가 템플릿 값을 표시하더라도 그 값의 의미와 명칭은 템플릿 등록 경계에서 온다. 인수인계의 질문·답변 방식이나 시간표의 배정 규칙을 Harnest 자체의 필수 흐름으로 설명하지 않는다.
